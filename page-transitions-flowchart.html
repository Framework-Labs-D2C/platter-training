1. Why SPA-like Navigation?

The reasoning behind intercepting browser navigation instead of letting Shopify handle full page loads.

Reasoning

The Problem with Full Page Loads in Shopify

Every Shopify page load means: DNS lookup, TLS handshake, HTML download, CSS/JS parse, Alpine.js init, store hydration, product data fetch, layout paint. That's 1-3 seconds of white screen even on fast connections. The merchant's brand experience resets on every click.

What Barba.js gives us: Intercepts <a> clicks, fetches the next page in the background, swaps only the <main> container, and keeps everything else alive — Alpine stores, header state, cart data, modal state, CSS, and all loaded JS. Navigation feels like 50-150ms instead of 1-3s.
This is NOT stock Barba.js. We run a custom implementation adjusted for Shopify. Key differences: custom URL normalization that strips Shopify tracking params from cache keys, collection URL deduplication (/collections/x/products/y → /products/y), a fetchFromCache utility that layers Barba's memory cache with IndexedDB persistence, and account route purging. The barba-prefetch plugin is also customized. Don't reference the stock Barba.js docs and expect 1:1 behavior.
Key insight: This is NOT a traditional SPA. Shopify still renders full HTML server-side for every route. Barba just replaces the content area client-side instead of letting the browser do a full reload. Server-side rendering is preserved for SEO and first load.

2. Layout Structure — The Barba Wrapper

How theme.liquid sets up the DOM for Barba.js to manage navigation.

1 Layout Structure

The Three-Layer DOM Setup

Barba needs a static wrapper (never changes) and a swappable container (replaced on each navigation). Everything outside the container persists across page transitions.

<body data-barba="wrapper"> <!-- PERSISTS: global sections, Alpine stores, header, footer --> <div data-globals-section>{% sections '0_global' %}</div> <!-- PERSISTS: transition overlay with animated logo --> {% section 'global_page_transitions' %} <!-- PERSISTS: header --> <header data-header-section>{% sections '0_header' %}</header> <!-- SWAPPED: this is what Barba replaces on navigation --> <main data-content-root data-barba="container" data-barba-namespace="tmp" data-template="{{ template }}" data-pathname="{{ request.path }}"> {{ content_for_layout }} {% section "data_product_json" %} </main> <!-- PERSISTS: footer --> <footer data-footer-section>{% sections '0_footer' %}</footer> </body>
Why data-barba-namespace="tmp"? We use a single namespace for all pages. Barba supports per-template namespaces for different transition animations, but we keep it simple — one universal slide transition. The data-template attribute is what the Alpine router store uses for template-aware logic.

4. Initialization Flow

What happens when the page first loads — from Alpine init to Barba being ready.

3 JavaScript

Bootstrap Sequence

Page transitions init is triggered by the alpine:init event. This ensures Alpine stores are available before Barba starts intercepting navigation.

// Triggered by: document.addEventListener("alpine:init", initPageTransitions) const initPageTransitions = () => { if (initialized) return; // guard against double-init // 1. Create the $router Alpine store Alpine.store("router", { pathname: rootContainer.getAttribute("data-pathname"), template: rootContainer.getAttribute("data-template"), search: window.location.search, hash: window.location.hash, }); // 2. If disabled or design mode, replace barba.go with native nav if (design_mode || !page_transitions_enabled) { barba.go = (href) => { window.location.href = href; }; } // 3. Enable barba-prefetch plugin (hover/viewport prefetching) barba.use(barbaPrefetch, { root: document.body, timeout: 4000 }); // 4. Restore cached barba pages from IndexedDB (10min TTL) idbKeyval.keys().then(res => { res.forEach(key => { // Restore barba-prefetch---{timestamp}-//-{url} entries if (+timestamp > Date.now() - 600000) { barba.cache.set(cacheKey, ...); // restore to memory cache } else { idbKeyval.del(key); // evict expired entries } }); }); // 5. 5. Navigation Lifecycle — The 6 Hooks

What happens at each stage when the user clicks a link. Barba fires these hooks in order.

Hook 1

beforeLeave

Fires immediately on link click, before any visual change. Used to clean up current page state.

// Close any open modals window._stores?.modal?.setId(""); window._stores?.modal?.setSubId("");
Why here? Modals overlay the transition. If we close them after the overlay appears, the user sees a flash of modal content behind the overlay.
Hook 2

leave (transition)

The visual transition begins. The overlay slides in from the left with the brand logo.

// Slide the overlay in transitionOverlay?.classList.add( "active", "out-active" ); // CSS handles the animation: // .active = opacity-100, translate-x-0 // .out-active = controls exit direction
Hook 3

afterLeave

Old page content is still in the DOM but hidden behind the overlay. Router store is updated with the new location.

routerStore.setValue("pathname", window.location.pathname); routerStore.setValue("search", window.location.search); routerStore.setValue("template", data?.next?.container?.getAttribute("data-template") );
Why update the router store here? Alpine components that react to $router.template (like header variants) need to update before the new content is visible, so the correct header state is ready when the overlay clears.
Hook 4

beforeEnter

New content is in the DOM but not yet visible. Clears deferred component states.

// Reset x-defer-active so lazy components // re-evaluate their intersection triggers data?.next?.container ?.querySelectorAll("[x-defer-active]") .forEach(el => el.removeAttribute("x-defer-active"));

enter (transition)

The overlay slides out, revealing new content. Handles scroll position with sticky header compensation.

afterEnter — The Big One

New content is visible. This hook does the heavy lifting: removes old container, re-executes scripts, re-initializes third-party widgets. This is where most bugs live.

6. Script Re-execution — The Hard Part

When Barba swaps the container, <script> tags in the new HTML are inert text. They must be manually re-executed.

4 Script Handling

The 5-Step Script Re-execution Pipeline

After a 60ms delay (to let Alpine process the new DOM), we parse the full HTML response and systematically re-inject scripts. The order matters.

// Step A: Re-execute product data init scripts // These set up window._recent_products and preload links const productDataContainer = data.next.container?.querySelector("[data-product-data-init]"); if (productDataContainer) { const newScript = document.createElement("script"); newScript.innerHTML = productDataContainer.innerText; document.head.appendChild(newScript); // executes immediately when appended } // Step B: Replace Shopify app blocks in-place // App blocks exist outside our container, so we match by ID html.querySelectorAll(".shopify-block.shopify-app-block").forEach(element => { const current = document.getElementById(element.id); current.parentNode.replaceChild(element, current); }); // Step C: Inject NEW external scripts (<script src="...">) // Only scripts NOT already in <head> — prevents double-loading html.querySelectorAll(":not([data-content-root]) script[src]").forEach(script => { if (!document.head.querySelector(`script[src*="${script.src.split('/').at(-1)}"]`)) { const newScript = document.createElement("script"); newScript.src = `${script.src}?v_id=${Date.now()}`; // cache bust document.head.appendChild(newScript); } }); // Step D: Re-execute inline scripts inside content root // Excludes: scripts with src, product data JSON, application/json document.querySelectorAll("[data-content-root] script:not(...)").forEach(script => { const newScript = document.createElement("script"); newScript.innerHTML = script.innerHTML; script.parentNode.replaceChild(newScript, script); }); // Step E: Re-execute content root scripts with src document.querySelectorAll("[data-content-root] script[src]").forEach(script => { const newScript = document.createElement("script"); newScript.src = `${script.src}?v_id=${Date.now()}`; // cache bust script.parentNode.replaceChild(newScript, script); });
Why replaceChild instead of just appendChild? When a <script> is inserted via innerHTML, the browser treats it as inert text. Creating a new <script> element and replacing the old one forces the browser to evaluate it. This is how all SPA-like frameworks handle script execution in dynamically inserted HTML.
Why cache-busting with ?v_id={timestamp}? Without it, the browser might serve the script from disk cache without re-executing. The timestamp ensures a fresh evaluation even if the URL is the same script.

7. Prefetch & Caching Layer

How pages are pre-loaded before the user even clicks, and how product data is extracted from prefetched HTML.

5 Data Flow

The Prefetch Pipeline

This runs in a requestIdleCallback so it never blocks the main thread.

// 1. User hovers a link (or it enters viewport) // barba-prefetch fetches the HTML in the background // 2. "barba:prefetch:fulfilled" fires // We intercept this event and extract product data from the HTML // 3. Parse the HTML, find all [data-product-data] script tags const div = document.createElement("div"); div.innerHTML = fetchResults?.data?.html; const productData = div.querySelectorAll(`[data-product-data]`); // 4. For each product found, merge into _products cache // Using the existing/IDB fallback pattern to preserve full data productData?.forEach(async (scriptElement) => { const product = JSON.parse(scriptElement.innerHTML); const existing = _products[product.handle] ?? (await idbKeyval.get(dbKey)) ?? {}; _products[product.handle] = { ...existing, ...(product?._full_data ? product : existing?._full_data ? existing : product), }; await idbKeyval.set(dbKey, _products[product.handle]); }); // 5. Cache the full barba response in IDB for cross-session reuse await idbKeyval.set(`barba-prefetch---${startTime}-//-${url}`, fetchResults);
Cross-session caching: Barba prefetched pages are stored in IndexedDB with a timestamp prefix. On the next page load, entries less than 10 minutes old are restored into Barba's memory cache. This means if a user returns within 10 minutes, previously prefetched pages are instantly available without re-fetching.
Product data pre-warming: The prefetch doesn't just cache HTML. It extracts product JSON from [data-product-data] script tags and merges them into the in-memory _products store. When the user navigates to that product, the data is already available — no loading state needed.

8. Custom Shopify Cache Layer (Not Stock Barba)

The caching and URL normalization layer that makes Barba work with Shopify's URL structure. This is entirely custom — not part of the Barba.js package.

6 Custom Shopify Logic

URL Normalization — getShopifyCacheUrl

Shopify appends tracking params, UTM params, and collection-scoped paths to URLs. Without normalization, the same page gets cached under dozens of different keys. This function is the backbone of our custom caching layer.

const getShopifyCacheUrl = (href: string) => { const url = new URL(href); const searchParams: string[] = []; for (const [key, value] of url.searchParams) { // ONLY keep params that change page content: if (key === "page") searchParams.push(`${key}=${value}`); if (key === "sort_by") searchParams.push(`${key}=${value}`); if (/^filter\./gi.test(key)) searchParams.push(`${key}=${value}`); // Everything else is STRIPPED: utm_*, fbclid, gclid, // _pos, _ss, _v, variant, selling_plan, etc. } // Sort params for consistent cache keys regardless of order const sorted = [...searchParams].sort(); // Normalize collection-scoped product URLs: // /collections/summer-sale/products/blue-shirt → /products/blue-shirt // This prevents duplicate cache entries for the same product return href.split(/[?#&]/)[0] .replace(/(\/collections\/[^/]*\/)/gi, "/") + (sorted.length ? `?${sorted.join("&")}` : ""); };
Why this matters: A single product like /products/blue-shirt can be reached via /collections/summer/products/blue-shirt?utm_source=email&fbclid=abc, /collections/new/products/blue-shirt?_pos=1&_ss=12, or just /products/blue-shirt. Without normalization, that's 3+ separate cache entries for identical content. With it, they all resolve to one key: /products/blue-shirt.
Only content-changing params survive: page (pagination), sort_by (collection sort), and filter.* (collection filters) are the only params that produce different server responses. Everything else is tracking or UI state that doesn't affect the HTML.

Custom Shopify Logic

fetchFromCache — Three-Tier Cache Layer

Beyond page transitions, we expose Barba's cache as a general-purpose fetch utility. This is used by sibling product loading, search, blog pagination, and anywhere else that fetches full Shopify pages.

const fetchFromCache = async (urlString, options) => { const cacheUrl = getShopifyCacheUrl(urlString); // Tier 1: Check Barba's in-memory cache let cache = barba.cache.get(cacheUrl); // Tier 2: Fall back to IndexedDB if (!cache?.request) { const key = (await idbKeyval.keys()) .find(k => k.includes(cacheUrl)); if (key) { cache = barba.cache.set(cacheUrl, idbKeyval.get(key).then(res => res?.data), "prefetch"); } } // Tier 3: Fetch from network (force-cache for CDN hits) if (!cache?.request) { const data = fetch(urlString, { credentials: "same-origin", cache: "force-cache", // CDN cache hit when possible }).then(res => res.text()).then(html => ({ html, url: ... })); cache = barba.cache.set(cacheUrl, data, "prefetch"); // Fire the prefetch event so product data gets extracted document.dispatchEvent( new CustomEvent("barba:prefetch:fulfilled", { detail: { url: cacheUrl } }) ); } return html; };
Why reuse Barba's cache for non-navigation fetches? If the user hovered a product link (triggering a prefetch), and then a section calls fetchFromCache("/products/blue-shirt") to load sibling data, it gets the already-cached HTML for free. One fetch serves both the transition and the data layer.

Custom Shopify Logic

Account Route Purging & Collection URL Cleanup

Two cleanup operations that run at different times to keep the cache safe.

// On init: purge any /account routes from Barba's cache // Account pages contain personal data that must never be served from cache [...(barba.cache.keys() ?? [])].forEach(key => { if (key.includes("/account")) { barba.cache.delete(key); } }); // On IDB restore: same check — delete account entries from IndexedDB res.forEach(async (key) => { if (key.includes("/account")) { idbKeyval.del(key); return; } // ... restore valid entries ... }); // On prefetch fulfilled: strip collection prefix from URL // e.detail.url.replace(/(\/collections\/[^/]*\/)/gi, "/") // Ensures handleRouteCaching receives the normalized URL
Security note: Account routes (/account, /account/orders, etc.) contain PII. If they were cached in IDB and the browser is shared, another user could see them served from cache. Both the Barba memory cache and IDB are purged on every initialization. These routes are also in the prefetchIgnore and cacheIgnore lists so they never enter the cache in the first place — the purge is a safety net.

9. Common Limitations & Gotchas

The things that break, why they break, and what you can do about them.

! Limitation

External Scripts That Bind Once

Many third-party scripts (reviews, loyalty, analytics) run once on DOMContentLoaded and assume they'll never need to run again. After a Barba transition, their DOM targets are gone but their event listeners point to removed elements.

Symptoms: Widget shows on first load but disappears after navigation. Or worse: widget appears but is non-interactive (click handlers bound to the old DOM).
Solutions (in order of preference):
1. Check for an API — many apps expose init() or refresh() methods. Call them in the afterEnter hook.
2. Re-fire DOMContentLoaded — we already do this, and it works for scripts that listen for it. But scripts that check document.readyState === 'loading' won't re-fire their handler because readyState is already 'complete'.
3. Add the route to ignore list — last resort. If a page depends heavily on a third-party script that can't be re-initialized, exclude it from transitions entirely.
Limitation

Scripts Using document.write()

document.write() after the page has loaded will replace the entire document. Some legacy third-party scripts use this pattern. There is no workaround — these routes must be excluded.

Limitation

Memory Leaks from Persistent Event Listeners

Event listeners added to window or document by scripts inside the swapped container are never cleaned up. After many navigations, hundreds of orphaned listeners can accumulate.

Our mitigation: Alpine.js handles this via its tree destruction (Alpine.destroyTree) for x-data components. But raw addEventListener calls in inline scripts or third-party code will leak. For internal scripts, prefer Alpine directives (@resize.window, @scroll.window) which auto-cleanup.
Limitation

readyState Checks vs Event Listeners

Scripts that use this pattern will NOT work after transitions:

// This BREAKS after Barba transitions: if (document.readyState === "loading") { document.addEventListener("DOMContentLoaded", init); } else { init(); // runs immediately, but only on first load } // This WORKS because we re-dispatch the event: document.addEventListener("DOMContentLoaded", init);
Why: After the initial page load, document.readyState is permanently "complete". The else branch runs immediately during script evaluation, which is fine. But if the script uses a module pattern that only calls init() inside the if branch (checking for "loading"), it will never fire again because the document is already loaded.
Limitation

Shopify App Blocks Need Special Handling

Shopify app blocks (.shopify-block.shopify-app-block) exist in the section group, not inside the Barba container. They're matched by ID and replaced in-place rather than swapped with the container.

Why this is fragile: If an app block changes its ID format, or if two app blocks have the same ID across different pages, the replacement will silently fail or target the wrong element. Always test app blocks across page transitions.

10. Render Tabs System

How sections can define tabbed content in Liquid, composed into functional tabs by the layout at render time.

6 Liquid Architecture

The Problem Render Tabs Solves

Shopify sections can't communicate with each other. If three sections inside a section group each want to define a tab, there's no way for them to coordinate a shared tab bar. Render Tabs solves this by post-processing the rendered HTML at the layout level using Liquid string manipulation.

Key insight: Sections render their content into a single capture variable. Before outputting it, we pass it through _layout.render_tabs which scans for marker tags, extracts tab labels, generates the navigation buttons, and wires up the Alpine data binding. All in pure Liquid — no JavaScript needed for the composition step.
Liquid

How Sections Declare Tabs

A section that wants to participate in tabs wraps its content with marker tags. These are custom HTML elements that get stripped out by the Render Tabs processor.

<!-- Inside a section's Liquid template --> <!-- 1. Declare which tab group this belongs to (0 or 1) --> <tab-content-group>0</tab-content-group> <!-- 2. Set the tab's label --> <tab-content-label>Description</tab-content-label> <!-- 3. The actual content (shown/hidden by Alpine) --> <div data-tab-group="0" data-tab-id="Description" x-show="$tabs[$el.closest('[id]').id]?.current_tabs[0] === 'Description'"> ... tab content here ... </div> <!-- 4. Declare where the tab navigation should appear --> <tab-navigation> <tab-label>[label]</tab-label> <!-- plain text label --> <tab-label-richtext>[label]</tab-label-richtext> <!-- rich label (can contain HTML) --> <tab-group>0</tab-group> <!-- which group's tabs to render --> <tab-button-class>my-tab-btn</tab-button-class> <!-- CSS class for buttons --> <tab-hover-trigger>false</tab-hover-trigger> <!-- tabs switch on hover? --> <tab-navigation-buttons-placeholder /> <!-- replaced with actual buttons --> </tab-navigation>
Liquid Processing

What _layout.render_tabs Does

The snippet receives the entire section group HTML as a single string and transforms it.

// Pseudocode of the Liquid processing: 1. Split HTML by 'id="shopify-section' to get individual sections 2. For each section that contains '<tab-content-label>': a. Extract all tab labels from <tab-content-label>...</tab-content-label> b. Group them by <tab-content-group>0|1</tab-content-group> c. For each <tab-navigation> block: - Read the button class, hover trigger, label template - Generate one <button> per tab label with Alpine @click bindings - Replace <tab-navigation-buttons-placeholder /> with the buttons - Strip the <tab-navigation> wrapper d. Add x-cloak to all tabs except the first (prevents flash) 3. Add data-tabs="{...}" and x-data="{..._sections.initTabs($el)}" to the section wrapper
The generated button markup:
<button type="button" @click="current_tabs[0] = 'Description'" :class="current_tabs[0] === 'Description' ? 'active' : ''" class="shrink-0 my-tab-btn"> Description </button>

JavaScript Runtime

The initTabs Alpine Component

When the section initializes, Alpine reads the data-tabs attribute and populates the $tabs store. It also sets up responsive breakpoint watchers to auto-switch tabs if the current tab becomes hidden (e.g. a tab with visible_if that hides on mobile).

// tabs.ts - simplified export const initTabs = ($el) => { const tabs = Alpine.store("tabs"); tabs[$el.id] = { tabs: raw_tabs.map(t => t.split("|%S%|")), current_tabs: raw_tabs.map(t => t.split("|%S%|")[0]), }; // Watch breakpoints to auto-switch hidden tabs [480, 640, 768, 1024, 1280, 1536].forEach(px => { matchMedia(`(min-width: ${px}px)`).addEventListener("change", ensureNoHiddenTabs); }); return tabs[$el.id]; };

Reasoning

Why This Architecture for Tabs?

This approach is unusual. Most tab systems use JavaScript to scan the DOM and generate navigation. Why does Accelerate-Z do it in Liquid?

1. No layout shift. Tab navigation is rendered server-side in the initial HTML. There's no JavaScript that runs, scans for tabs, then injects buttons — which would cause a visible layout shift.

2. Sections stay independent. Each section declares its tabs without importing anything or knowing about its siblings. The layout composes them together. This is the same principle as Alpine stores — decoupled producers and consumers.

3. Theme Editor compatibility. Because tabs are in the HTML, the Theme Editor can show/hide sections and the tab navigation updates on the next render. A JS-based system would need custom editor integration.

4. Two tab groups per section. The <tab-content-group>0|1</tab-content-group> system allows a section to have two independent tab bars (e.g. main content tabs + sidebar tabs) without additional complexity.

11. Liquid Variable Hacking for Theme Blocks

Techniques for getting data in and out of places Shopify doesn't want you to.

7 Liquid Technique

The Problem: Sections Can't Share Variables

In Shopify Liquid, each section renders in isolation. You can't assign a variable in Section A and read it in Section B. But sometimes you need cross-section coordination — like telling the header what color scheme the hero is using, or passing product data between a PDP and a recommendations section.

The workaround: The layout captures all section HTML into a string variable, then manipulates that string before outputting it. Since the HTML is just a string at that point, you can split, replace, and recombine it freely.
Liquid Technique

Pattern 1: Capture & Post-Process

This is what Render Tabs uses, and the pattern extends to any cross-section transformation. The layout captures the full output, then runs it through processing snippets.

<!-- layout/theme.liquid --> <!-- Capture all header sections into a single string --> {% capture content %}{% sections '0_header' %}{% endcapture %} <!-- Run the string through a processing snippet --> {% render '_layout.merge_styles', input: content %} <!-- Or the Render Tabs processor --> {% render '_layout.render_tabs', content: core_content %} <!-- The snippet can split/replace/recombine the HTML string before it's output to the page -->
Key enabler: {% sections 'group_name' %} renders all sections in a group and returns their combined HTML. By capturing this into a variable instead of outputting it directly, we get a chance to transform it.
Liquid Technique

Pattern 2: Marker Tags as Data Channels

Custom HTML elements like <tab-content-label> are intentionally used as structured markers. The browser ignores unknown tags, so even if the processing fails, they're harmless in the output.

<!-- Section outputs a marker (invisible to the user) --> <tab-content-label>Reviews</tab-content-label> <!-- Layout snippet extracts it via string splitting --> {% assign tab_content = section_html | split: '<tab-content-label>' %} {% assign tab_label = tab_content.last | split: '</tab-content-label>' | first %} <!-- Now tab_label = "Reviews" and can be used to build navigation -->
Why custom elements? They're valid HTML (browsers won't error), they have clear open/close tags for string splitting, and they're self-documenting. Using data-* attributes would work too but requires more complex regex-like splitting in Liquid.
Liquid Technique

Pattern 3: Style Extraction & Consolidation

The _layout.merge_styles snippet demonstrates another variable hack: extracting all <style> tags from individually rendered sections and consolidating them into a single block. This prevents duplicate CSS and reduces render-blocking resources.

<!-- Simplified pattern from theme.liquid modal rendering --> {% assign content = content | replace: '<style></style>', '' | append: " " %} {% assign content_array = content | split: "</style>" %} {% assign styles_content = '' %} {% assign content = '' %} {% for split in content_array %} {% if forloop.last %} {% assign content = content | append: split %} {% break %} {% endif %} {% assign splits = split | split: "<style" %} {% assign content = content | append: splits.first %} {% assign styles_content = styles_content | append: splits.last %} {% endfor %} <!-- Output: one <style> block + style-free HTML --> <style>{{ styles_content | strip_newlines }}</style> {{ content }}
Reasoning

Why This Works (and When It Doesn't)

Liquid variable hacking is powerful but has real limitations.

Works well for
• Server-rendered composition (tabs, style merging)
• Extracting metadata from sections (labels, groups)
• Conditional layout based on section content
• Reducing duplicate CSS across sections
• Any transformation that only needs the HTML string
Breaks down when
• Sections render asynchronously (they don't in Liquid, but app blocks can)
• The marker tag content contains the same delimiter used for splitting
• You need to pass complex data (nested JSON) — string splitting gets brittle
• Theme Editor needs to reflect changes instantly (requires full re-render)
• Performance: O(n) string ops on large section group HTML
Rule of thumb: If you need server-side cross-section coordination, use the capture → process → output pattern. If you need client-side coordination, use Alpine stores. Don't try to do client-side work in Liquid or server-side work in JavaScript.
