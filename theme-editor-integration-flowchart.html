1. How the Theme Editor Works

The iframe sandbox, re-render cycle, and what Shopify controls vs. what we control.

1 Architecture

The Editor Is an Iframe

When a merchant opens Online Store → Customize, Shopify loads the admin UI in the parent frame and your theme in a child <iframe>. The admin sidebar and your storefront are separate documents communicating via postMessage.

Key implication: The admin UI can re-render individual sections independently. When a merchant changes a setting, Shopify re-renders just that section's Liquid on the server and swaps the HTML into the iframe. Your JavaScript must be ready for DOM nodes to appear and disappear at any time. This is why Accelerate-Z centralizes all editor event handling in a single editor.ts file.
Architecture

The Re-Render Cycle

Every time a merchant changes a section or block setting in the sidebar, this cycle runs:

This is why Liquid-first rendering matters. If your component relies purely on JavaScript to render its UI, the merchant sees nothing in the editor until JS runs. Server-rendered Liquid output is visible immediately after the HTML swap. Alpine.js is inherently editor-friendly because it walks the new DOM for x-data attributes and auto-initializes — no manual binding step needed after a re-render.

2. Detecting Design Mode — Three Flags

Not two — three. Each serves a different purpose across Liquid and JavaScript.

Liquid

Flag 1: request.design_mode

Returns true when the page is being rendered inside the Theme Editor. Available in every Liquid template. This is the primary gate for editor-specific HTML output.

<!-- Gate expensive operations to editor only --> {% if request.design_mode %} <script type="application/json" data-primary-product-data> {% render '_json.product', product: product, card: false %} </script> {% endif %}
Liquid

Flag 2: request.visual_preview_mode

Returns true when Shopify is rendering a visual preview (e.g. theme thumbnails in the admin themes list). This is not the same as design mode. Accelerate-Z uses it extensively alongside request.design_mode to handle different editor contexts.

<!-- theme.liquid: Different rendering paths for each mode --> <!-- Design mode but NOT visual preview: load full section groups --> {% if request.design_mode == true and request.visual_preview_mode != true %} {% sections '0_head' %} {% endif %} <!-- Visual preview mode: render styles for visual preview --> {% if request.design_mode == true %} {% render "_layout.load_visual_preview_styles" %} {% endif %} <!-- Production OR visual preview: optimize section loading --> {% if request.design_mode != true or request.visual_preview_mode == true %} {% capture head_sections %}{% sections '0_head' %}{% endcapture %} <!-- Clean and output optimized --> {% endif %}
layout/theme.liquid:346-415
JavaScript

Flag 3: window.design_mode (Set from Liquid)

In Accelerate-Z, the client-side flag is not read from Shopify.designMode directly. Instead, Liquid sets window.design_mode in the global settings snippet. This is the flag all TypeScript files check.

<!-- snippets/_layout.global_settings.liquid (line 38) --> <script> window.design_mode = {{ request.design_mode }}; </script> // Then in TypeScript: if (window.design_mode) { document.dispatchEvent(new CustomEvent("theme:editor:init")); }
snippets/_layout.global_settings.liquid:38, assets/theme.ts:17
Pattern

When to Use Which Flag

Flag Context Use For
request.design_mode Liquid (server) Extra HTML, inline JSON, fallback styles, section group loading
request.visual_preview_mode Liquid (server) Theme thumbnail rendering, optimized section output, skip editor-only sections
window.design_mode JS (client) Trigger editor init, disable features, guard production-only code

design_mode and visual_preview_mode often appear together because the code needs to handle three distinct rendering contexts: (1) full Theme Editor with sidebar, (2) visual preview thumbnail, and (3) production. Many conditionals combine both flags to distinguish between these paths.

3. The Centralized editor.ts & $editor Store

All Theme Editor integration lives in one file. It manages an Alpine store that the entire theme reacts to.

2 JavaScript

The EditorStore Type

A single Alpine store tracks all editor state. Every component in the theme can reactively watch this store via the $editor magic property.

// assets/editor.ts — the type definition export type EditorStore = { load_section_id: string; // section just loaded/re-rendered unload_section_id: string; // section just removed select_section_id: string; // section currently selected in sidebar reorder_section_id: string; // section just reordered via drag select_block_id: string; // block currently selected in sidebar deselect_block_id: string; // block just deselected deselect_section_id: string; // section just deselected inspector: boolean; // inspector tool active? };
assets/editor.ts, assets/types.d.ts:77-89
JavaScript

Initialization Flow

The editor system initializes through a custom event chain, not on page load. This keeps it completely inert in production.

// 1. theme.ts — initTheme() runs on "alpine:init" if (window.design_mode) { document.dispatchEvent(new CustomEvent("theme:editor:init")); } // 2. editor.ts — listens for "theme:editor:init" document.addEventListener("theme:editor:init", () => { // Register all 9 Shopify event listeners // Initialize empty block detection // Set up inspector message listener }); // 3. Store created in initTheme(), magic registered globally Alpine.store("editor", { /* EditorStore defaults */ }); Alpine.magic("$editor", () => Alpine.store("editor"));
assets/theme.ts:3-24, assets/editor.ts:40-265
Dual state tracking: Every store update also writes to window.Shopify.editor. This keeps a plain JS object in sync alongside the Alpine reactive store, so non-Alpine code (third-party scripts, vanilla JS) can also read editor state.
JavaScript

Using $editor in Components

Any Alpine component can react to editor state changes using x-effect or x-show with the $editor magic. This is the core of how blocks respond to Theme Editor actions.

<!-- In a Liquid template — reactive block selection --> <div x-data x-effect="if ($editor.select_block_id === '{{ block.id }}') { utils.scrollToX(0, $el.offsetLeft, $el.closest('.scroll-container')) }"> <!-- This runs every time $editor.select_block_id changes --> <!-- No addEventListener needed — Alpine reactivity handles it -->
This is the critical architectural difference. Accelerate-Z does NOT use imperative document.addEventListener("shopify:block:select", ...) in components. Instead, editor.ts handles all Shopify events centrally and updates the $editor store. Components react to store changes via Alpine's built-in reactivity. This is more declarative, less error-prone, and automatically handles cleanup.

4. Editor Events & Lifecycle (All 9)

Shopify dispatches 9 events inside the theme iframe. All are captured centrally in editor.ts and re-dispatched as custom events.

Editor Events

Section Events (5)

shopify:section:load

The most complex handler. Fires when a section is added or re-rendered. Parses tab marker elements (<tab-content-group>, <tab-navigation>), rebuilds Alpine tab bindings, consolidates <style> tags into the section root, replaces stale section IDs in CSS, and dispatches editor-load--{sectionId}.

shopify:section:unload

Fires when a section is removed. Updates $editor.unload_section_id and dispatches editor-unload--{sectionId}. Components watching the store clean up automatically.

shopify:section:select

Fires when the merchant clicks a section in the sidebar. Sets $editor.select_section_id, clears select_block_id. Dispatches editor-select--{sectionId}. Does not re-render.

shopify:section:deselect

Fires when the merchant clicks away from a section. Sets $editor.deselect_section_id, clears select states. Dispatches editor-deselect--{sectionId}.

shopify:section:reorder

Fires when a section is reordered via drag-and-drop in the sidebar. Sets $editor.reorder_section_id and dispatches editor-reorder--{sectionId}.

Editor Events

Block Events (2)

shopify:block:select

Fires when a merchant clicks a block in the sidebar. Sets $editor.select_block_id. Components react via x-effect to reveal hidden blocks (switch tabs, open accordions, scroll carousels). Dispatches editor-select--{blockId}.

shopify:block:deselect

Fires when the merchant clicks away from a block. Sets $editor.deselect_block_id, clears select_block_id. Dispatches editor-deselect--{blockId}.

Editor Events

Inspector Events (2)

shopify:inspector:activate

Fires when the merchant activates the inspector tool (the crosshair icon that lets them click elements to select them). Sets $editor.inspector = true and syncs to window.Shopify.editor.inspector.

shopify:inspector:deactivate

Fires when the inspector is turned off. Sets $editor.inspector = false.

Inspector also uses postMessage. When the merchant clicks an element via the inspector, Shopify sends a window.message with type: "StorefrontMessage::SelectElement" containing blockDomId and sectionGid. The message handler in editor.ts updates $editor.select_block_id and $editor.select_section_id accordingly.
assets/editor.ts:246-262, 283-325
JavaScript

Custom Event Re-Dispatching

Every Shopify event is re-dispatched as a namespaced custom event. This lets individual sections listen for their own events specifically, without filtering by section ID.

// editor.ts dispatches scoped events for each Shopify event: // On shopify:section:load for section "template--123__main": document.dispatchEvent(new CustomEvent("editor-load--template--123__main")); document.dispatchEvent(new CustomEvent("editor_load")); // On shopify:block:select for block "block_abc123": document.dispatchEvent(new CustomEvent("editor-select--block_abc123")); // Usage: a section can listen for its own load event document.addEventListener("editor-load--{{ section.id }}", () => { // Reinitialize only when THIS section reloads reinitAceEditor(); });
assets/editor.ts, snippets/_components.editor_preview.liquid:102

5. Block Select, Tab Focus & Collapsible Auto-Open

The most important editor UX: when a merchant clicks a block, the UI reveals it — via reactive Alpine effects, not imperative event listeners.

3 Editor Event

The Problem: Hidden Blocks

Tabs show one panel at a time, accordions collapse sections, carousels show one slide. When a merchant clicks a block in the sidebar that's inside hidden content, they expect to see it. The editor selects the block's DOM element, but if it has display: none or is behind an Alpine x-show, the merchant sees nothing.

This is the #1 source of "it's broken" support tickets for theme blocks. The merchant adds a block, clicks it in the sidebar, can't see it because it's inside an inactive tab or collapsed accordion.
JavaScript — Reactive Pattern

Tab Switching via $editor + x-effect

Accelerate-Z does NOT use addEventListener("shopify:block:select", ...) in tab components. Instead, the editor events update $editor.select_block_id in the Alpine store, and tab content blocks react to it with x-effect.

<!-- blocks/tab_content/tab_content.liquid --> <!-- Each tab content block watches $editor reactively --> <div x-data="{ index: +`{{ tab_group | default: 0 }}` }" x-show="$data.current_tabs[index] === '{{ label }}'" x-effect=" // When editor selects a block inside this tab, switch to it if ($editor?.select_block_id === `{{ block.id }}` || $el.querySelector(`[data-style-id='{{ section.id }}--${$editor?.select_block_id}']`)) { $data.current_tabs[index] = '{{ label }}'; } // Also handle URL hash navigation if ($router.hash.replace(/#/gi,'') === '{{ hash_target }}') { $data.current_tabs[index] = '{{ label }}'; } " {{ block.shopify_attributes }} >
blocks/tab_content/tab_content.liquid:23-42
Why reactive instead of imperative? The x-effect approach means: (1) no manual cleanup on section:unload — Alpine handles it, (2) the effect runs for any block selection change, not just the initial one, (3) the same pattern handles both editor clicks and URL hash navigation, (4) it's co-located with the display logic (x-show) so the relationship is visible.
JavaScript

Collapsible / Accordion Auto-Open

Collapsible blocks use the same reactive pattern but with more sophisticated state tracking. When the editor selects a block inside an accordion, it opens. When deselected, it closes — but only if the editor opened it, not if the user had it open already.

// assets/collapsible.ts (line 106) if (window.Shopify.designMode) { const editor = Alpine.store("editor") as EditorStore; Alpine.effect(() => { // Build the composite style ID for matching const style_id = `${editor.select_section_id}--${editor.select_block_id}`; if ($el.getAttribute("data-style-id") === style_id || $el.querySelector(`[data-style-id="${style_id}"]`)) { // Block is inside this collapsible — force open toggleOpen(true); state.themeEditorControl = true; // track that editor opened it } else { if (state.themeEditorControl) { // Editor had opened this, now deselected — close it state.themeEditorControl = false; toggleOpen(false, true); } // If user opened it manually, leave it alone } }); }
assets/collapsible.ts:106-121
The themeEditorControl flag is key.

Without it, deselecting a block would close every accordion — even ones the merchant opened manually while browsing. The flag tracks whether the editor forced the open, so only editor-opened accordions close on deselect. User-opened ones stay open.

JavaScript

Carousel / Scroll-Based Block Reveal

For blocks inside horizontal scroll containers (carousels, card sliders), Accelerate-Z uses editor-only x-effect directives injected via request.design_mode in Liquid.

<!-- Injected only in design mode --> {% if request.design_mode %} x-effect="if ($editor.select_block_id === `{{ block.id }}`) { utils.scrollToX(0, $el.offsetLeft, $el.closest('.scroll-container')) }" {% endif %}
blocks/cards_testimonial/cards_testimonial.liquid, blocks/slide/slide.liquid

6. Schema Design — TypeScript Schemas

In Accelerate-Z, schemas are defined in TypeScript files with full type safety — not inline JSON in {% schema %} blocks.

4 Schema

Schema File Architecture

Each block and section has two TypeScript files that define its editor configuration. These are compiled into the Liquid {% schema %} output at build time.

_schema.ts — Settings
export const button: ShopifyThemeBlock<ButtonBlock> = { name: "Button", category: "Basic", settings: [ { type: "select", id: "type", label: "Type", // ... }, { type: "color", id: "text_color", label: "Text color", }, ...universalBlockGlobals(), ], tag: null, };
_presets.ts — Editor Defaults
export const presets: ShopifySectionPreset<ButtonSection>[] = [ { name: "Button", category: "Basic", manual_preset: true, settings: { text_color: "#ffffff", background_color: "#272824", custom_css: `:root { ... }`, }, blocks: [ /* nested */ ], } ];
blocks/button/_schema.ts, blocks/button/_presets.ts
Why TypeScript? Type safety catches schema errors at build time (wrong setting type, missing required fields). Shared utilities like universalBlockGlobals() keep common settings (text_color, background_color, custom_css) consistent across all blocks without duplication.
Schema

visible_if — Conditional Settings in the Editor

Settings can be conditionally shown or hidden in the editor sidebar using visible_if with Liquid-like expressions. This declutters the UI by only showing relevant settings based on the merchant's choices.

{ type: "url", id: "url", label: "Url", visible_if: "{{ block.settings.dynamic_content_type != 'metafield' and block.settings.type == 'button' or block.settings.type == 'link' }}", }
blocks/button/_schema.ts:57-78
Liquid

shopify_attributes — The Editor Binding

Every rendered block must output {{ block.shopify_attributes }} on its wrapper element. This generates data-shopify-editor-block with metadata the editor needs to highlight, select, and reorder blocks.

<!-- blocks/button/button.liquid --> <nav data-style-id="{{ section.id }}--{{ block.id }}" {{ block.shopify_attributes }} class="..." > <!-- block content --> </nav> <!-- shopify_attributes outputs: data-shopify-editor-block='{"id":"block_abc","type":"button",...}' -->
Without shopify_attributes, the block is invisible to the editor. It won't highlight on hover, can't be selected in the preview, and the inspector tool won't find it. This is the most common cause of "blocks don't work in the editor."

8. Empty Block Hiding & Editor Affordances

How empty blocks are handled differently in production vs. the editor, and the visual feedback system.

6 Liquid

The <script type="block/hide"> Pattern

In production, empty blocks output a <script type="block/hide"></script> tag that triggers client-side hiding. In design mode, these scripts are not output so merchants can always see and configure empty blocks.

<!-- Used in 50+ block files — the hide-if-empty pattern --> {% if request.design_mode != true and hide_conditionally contains '<script' %} {{ hide_conditionally }} <!-- Outputs: <script type="block/hide"></script> --> {% break %} {% endif %} <!-- In design mode: block always renders, even if empty -->
JavaScript

9. CSS Scoping & Live Updates

How data-style-id enables scoped styles and how section:load prevents CSS conflicts.

7 Pattern

The data-style-id Selector Replacement

Every block outputs styles using & as a placeholder selector, which Liquid replaces with a [data-style-id="..."] attribute selector. This scopes all CSS to that specific block instance.

<!-- blocks/button/button.liquid --> {% capture selector %}[data-style-id="{{ section.id }}--{{ block.id }}"]{% endcapture %} {% capture css %} & { color: {{ text_color }}; background: {{ background_color }}; } &:hover { opacity: 0.8; } {% endcapture %} <style>{{ css | append: custom_css | replace: '&', selector | strip_newlines }}</style> <!-- Outputs: [data-style-id="section123--block456"] { color: #fff; background: #000; } [data-style-id="section123--block456"]:hover { opacity: 0.8; } -->
blocks/button/button.liquid:78-92
JavaScript

CSS Consolidation on section:load

When the editor re-renders a section, the new HTML arrives with its own <style> tags. To prevent duplicate styles (old section + new section both having styles), editor.ts moves all style tags into the section root and invalidates old selectors.

// editor.ts — section:load handler (lines 146-154) // 1. Move all <style> tags into the section element section_el.querySelectorAll("style").forEach(style => { section_el.prepend(style); }); // 2. Replace old section IDs in CSS to prevent conflicts // Old selectors become: "overwritten-css-elements-not-in-use" // This prevents the previous section instance's styles from // bleeding into the new one
assets/editor.ts:92-168
Why this matters: Without CSS consolidation, when a merchant changes a color setting, the section re-renders with new styles, but the old section's <style> tag may still exist in the DOM. Both compete for specificity. The consolidation step ensures only the new section's styles apply.
JavaScript

Tab Rebuilding on section:load

The most complex part of the section:load handler: parsing tab marker elements from the new HTML and rebuilding Alpine bindings.

// editor.ts — section:load tab reconstruction (lines 92-145) // 1. Parse tab-content-group and tab-content-label elements const tab_blocks = [[], [], []]; // Up to 3 tab groups section_el.querySelectorAll("tab-content-group").forEach((group) => { const group_index = +group.textContent.trim(); // Extract label, add to tab_blocks[group_index] group.remove(); // Clean up marker elements }); // 2. Find tab-navigation placeholders, generate Alpine buttons section_el.querySelectorAll("tab-navigation").forEach((nav) => { // Extract: tab-label, tab-group, tab-button-class, tab-hover-trigger placeholder.innerHTML = tab_blocks[group_index] ?.map((label) => `<button @click="current_tabs[${group_index}] = '${label}'" :class="current_tabs[${group_index}] === '${label}' ? 'active' : ''" >${label}</button>`).join(""); }); // 3. Store structure and init Alpine section_el.setAttribute("data-tabs", JSON.stringify(tab_blocks.map(g => g.join("|%S%|")))); section_el.setAttribute("x-data", "{ ..._sections.initTabs($el) }");

10. Features Disabled in the Editor

Features that conflict with the editor and are guarded by window.design_mode.

! Warning

Page Transitions (Barba.js)

SPA-style navigation is always disabled in the editor. The editor manages its own navigation. If Barba intercepted link clicks inside the iframe, it would break the editor's template switching.

// page-transitions.ts (line 69) if (design_mode || !page_transitions_enabled) { barba.go = (href) => { window.location.href = href; }; }
assets/page-transitions.ts:69, 93, 138
Warning

IndexedDB / Route Cache

The IndexedDB route cache and SWR product data cache are disabled in design mode. Merchants need fresh data reflecting their current edits, not stale cached responses.

When development__disable_animations is enabled in design mode, all CSS animations and transitions are killed globally. This speeds up the editor experience during development.

11. Testing & Common Pitfalls

The testing routine and the mistakes that catch teams off guard.

8 Testing Checklist

Editor Testing Routine

1. Add the section/block. Does it appear in the sidebar? Can the merchant add it?

2. Change every setting. Toggle each one — does the preview update? Check visible_if conditions: do settings show/hide correctly?

3. Click each block. Does it highlight? If inside a tab: does the tab switch? Inside an accordion: does it open? Inside a carousel: does it scroll?

4. Test empty states. Remove all content from a block. Does it show the "Empty Block Hidden" feedback in the editor? Does it hide correctly in production?

5. Reorder blocks. Drag blocks in the sidebar. Does the preview reorder?

6. Remove and re-add. Delete a block and add it back. Does the section still work? Styles still apply?

7. Test the inspector. Activate the inspector tool and click elements in the preview. Does it select the correct block in the sidebar?

8. Switch templates. Navigate between templates. Does the section reinitialize cleanly?

Mental Model

The Golden Rule of Editor Integration

Build as if your section will be added, configured, removed, re-added, reordered, and clicked in rapid succession — because in the editor, it will be.

Your Liquid must render correctly in isolation (no assumed global state).
Your JS must initialize cleanly from a fresh DOM (editor.ts + Alpine handle most of this).

Theme Editor Integration Checklist

Server-side (Liquid):
• Use request.design_mode and request.visual_preview_mode for conditional rendering
• Always output {{ block.shopify_attributes }} on block wrappers
• Always output data-style-id="{{ section.id }}--{{ block.id }}" for CSS scoping
• Gate hide-if-empty scripts with request.design_mode != true
• Provide fallback product data and inline styles in design mode
• Inject editor-only x-effect attributes for scroll-to-block behavior

Client-side (JavaScript):
• All editor events handled centrally in editor.ts — don't add standalone listeners
• React to $editor store changes via Alpine x-effect, not imperative listeners
• Track themeEditorControl state for forced visibility (accordions, modals)
• Guard production-only features with window.design_mode

Schema (TypeScript):
• Define in _schema.ts + _presets.ts with proper types
• Use visible_if to conditionally show settings based on other setting values
• Use universalBlockGlobals() for consistent shared settings
• Block types need globally unique names following the naming convention
